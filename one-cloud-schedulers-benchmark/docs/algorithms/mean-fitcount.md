# Mean FitCount and bounded candidate portfolios

## Selection rule

In one-cloud terms, let `h` be a minion, `C[h]` its remaining physical
capacity, and `r` a sample resource request. A sample can contain a pod together
with its regular shards. Let `w[r]` be the sample weight: in this benchmark it
is the number of occurrences of the same physical shape in the declared
catalogue population. The runner supports two explicit weight modes:

- `--catalogue-weights sampled` preserves historical occurrence counts inside
  the selected catalogue (the default).
- `--catalogue-weights full` retains the exact population frequency of each
  selected physical shape before limiting the catalogue. It does not add
  unselected shapes or count create/delete events and repeated lifetimes.

The selected requests remain unchanged. Duplicate selected representatives of
one physical shape do not multiply its population frequency. Absolute weights
matter for a numeric total-fit limit: a catalogue of 32 representatives must not
silently replace instance counts with numbers from 1 to 32 when interpreting a
production threshold. Full weights can also change the lexicographic sample
order when the total-fit limit is disabled. Compare all participants in the
same weight mode and record the weight checksum and covered population mass.
The catalogue-aware physical FitCount definitions in this guide accept full
weights. Legacy factories, including masked/search/CatBoost refiners, reject
that explicit mode instead of silently dropping the frequencies. Their default
sampled mode and existing array-based Java API remain unchanged.

`F(r, C[h])` is the number of additional copies that the common physical
allocator can place, capped by `fitCap`. It counts copies on one minion, not
eligible minions. NUMA and device geometry participate in this calculation.
The copies do not increment affinity/dependency counters or apply the sample's
external candidate mask. Actual candidate assignments pass the full validator.

For an actual candidate assignment `a` on `h`, define

```text
T[r]       = sum_h F(r, C[h])
scarcity[r]= T[r] / w[r]
loss[r,a]  = F(r, C[h]) - F(r, C[h] after the complete assignment a)
```

Both selectors begin with the same feasible host/NUMA plans generated by
`GreedyPlanner`. They do not enumerate every possible disk layout. The physical
probe is greedy, so a loss can be negative; neither selector clamps it to zero.

Ordinary `fitcount` sorts samples by increasing `scarcity`, with first catalogue
occurrence breaking ties. It minimizes the vector of losses lexicographically:
minimize loss for the first sample, then for the second among surviving plans,
and so on. A loss for an earlier sample cannot be compensated by improvements
for later samples.

`mean-fitcount` instead minimizes

```text
sum_r w[r] * loss[r,a] / sum_r w[r]
```

The denominator is common to every candidate, so the implementation compares
integer numerators. This is a frequency-weighted mean of copy losses. It is not
an average over minions, a relative loss divided by `T[r]`, or a direct measure
of admitted CPU/RAM/GPU. Equal final scores use the same seeded tie-breaking.

## Production-style total-fit limit

`maxTotalFit=0` disables the limit and preserves the historical benchmark rule.
A positive value is a floor for the effective limit, matching the intent of
one-cloud's `max_total_fit`:

```text
usedCPU = max(0, totalCPU - freeCPU)
usedRAM = max(0, totalRAM - freeRAM)
growth  = min(totalCPU/usedCPU, totalRAM/usedRAM)
limit   = max(maxTotalFit, growth)
```

Only present dimensions with positive usage contribute a ratio. If neither
dimension has usage, growth is unbounded. Totals are immutable host supplies;
free resources come from the current context. The standalone runner has no
production control cycles, so it evaluates the limit before each request.

Only samples with `scarcity[r] <= limit` participate. This is inclusive and
frequency-normalized. The same gate applies to lexicographic and mean scoring;
mean uses the weights of the participating samples. If none participates, all
retained feasible plans tie. The limit does not reject an otherwise feasible
request.

The cache uses existing conservative lower bounds to avoid refreshing samples
already proved to exceed the limit. It never prunes a candidate from a partial
mean-loss sum: subsequent signed losses can improve the sum.

`maxTotalFit` is exposed only by the physical FitCount, RandomN, portfolio and
RL-pool definitions that implement this gate. Existing masked/window/search
definitions retain their previous contracts.

## Why a smaller candidate set can admit more requests

Consider two minions with free CPU/RAM `A=(6,6)` and `B=(5,7)`, and the stream
`Q,S,S,R`, where `Q=(4,4)`, `S=(3,3)`, and `R=(5,7)`. The catalogue has exactly
these frequencies: one Q, two S, one R. Use an unlimited total-fit limit.

| Sample | Copies on A | Copies on B | Total / frequency |
| --- | ---: | ---: | ---: |
| R | 0 | 1 | 1 |
| S | 2 | 1 | 1.5 |
| Q | 1 | 1 | 2 |

For the first Q, the loss vectors in R/S/Q order are `(0,2,1)` on A and
`(1,1,1)` on B. Lexicographic FitCount chooses A to preserve R. The next S goes
to B, destroying that remaining R opportunity anyway; the second S and R fail.
Two requests are admitted.

If the first shortlist retained only B, both following S requests would fit on
A: three requests are admitted. Mean also chooses B, because its weighted losses
are `5` on A and `4` on B. All capacities, samples, frequencies and constraints
are identical. A smaller candidate set cannot improve the minimum local
lexicographic objective, but that objective is not an optimum for the future
stream. This example illustrates candidate restriction, not the default
Random20 quota on a two-host cluster.

## Implemented combinations

| ID | Candidate plans | Final comparison |
| --- | --- | --- |
| `mean-fitcount` | All generated feasible plans | Mean |
| `randomn-mean-fitcount` | Random N, default 28 | Mean |
| `portfolio-mean-fitcount` | Random20 union fragmentation4 union LeastAllocated4 | Mean |
| `rl-pool-mean-fitcount` | Random20 plus up to 8 policy proposals from an auxiliary pool of up to 44 | Mean |
| `geometric-portfolio-mean-fitcount` | Random20 union LeastAllocated4 union geometric4 | Mean |

Quotas count plans, not distinct hosts. Unions deduplicate source indices and do
not refill overlaps. All plans are generated before shortlisting. The geometric
source minimizes the existing normalized residual squared-L2 score. It changes
neither assignments nor the old portfolio's fragmentation source. RL-pool reuses
the packaged actor without retraining it for the new final mean objective.
Population weighting affects the final FitCount refiner. Auxiliary fragmentation
scorers keep the selected request occurrences and their original sample
frequencies; LeastAllocated, geometric scoring and PPO features are unchanged.

The new combinations retain sequential `schedule(Request[])` semantics. They
do not jointly optimize an announced window or relocate existing placements.

## What portfolio fragmentation measures

The fragmentation source selects the lowest signed change in a workload-based
potential, `potential(after) - potential(before)`. This is a surrogate; it is
not the number of rejected requests or the percentage of all unusable resources.
Its samples are individual catalogue members, grouped with occurrence weights.
The GPU branch adapts the workload-aware unusable-resource measure from
[FGD (USENIX ATC 2023)](https://www.usenix.org/system/files/atc23-weng.pdf).
The CPU/RAM branch below is this benchmark's continuous unmatched-resource
proxy; it is not a standard CPU/RAM fragmentation percentage from that paper.

In the aggregate GPU model, let free host CPU/RAM be `(c,m)`, and a sample demand
be `(u,v)`. For positive demands, pair a continuous number of copies

```text
t = min(c/u, m/v)
unpaired = (c-t*u)/maxHostCPU + (m-t*v)/maxHostRAM
potential = sum_sample frequency * unpaired
```

Maximum host supplies normalize the two units. HW-core demand is converted with
the selected host's CPU power, and memory-backed disks contribute RAM. A CPU-only
sample leaves all RAM unpaired; a RAM-only sample leaves all CPU unpaired.

For sample `(1,1)` and normalization scales `(10,10)`, placing `(2,1)` on free
`(8,2)` changes the potential from `0.6` to `0.5` (delta `-0.1`). Placing it on
`(4,4)` changes `0` to `0.1` (delta `+0.1`). The first option consumes part of an
existing CPU surplus; the second creates an imbalance. Compare changes, not
the absolute potentials after placement.

In `devices20`, the source instead measures GPU shares unusable for each
catalogue CPU/GPU profile. A GPU has 20 shares. If CPU or the required GPU
geometry does not fit, all free shares are unusable for that profile. Otherwise
shares on cards below the required chunk size, and shares of an unneeded GPU
type, are unusable. Profiles without GPU also contribute all free GPU shares.
The potential is the sum of these shares times profile frequencies. RAM,
storage and policy eligibility are outside this auxiliary potential.

The branch is selected by the model, not the current request. In `devices20`
a host with no GPU has zero GPU potential before and after placement. A cloud
without any GPU therefore gets zero fragmentation scores; its four proposals
come from deterministic tie-breaking. There is no automatic CPU/RAM fallback.

LeastAllocated is a different source: maximize the integer free-capacity
percentage after placement, first averaged over cells within a resource family,
then over present families. It does not use catalogue frequencies. See the
existing Kubernetes scorer for exact rounding and cell selection.

## Performance and comparisons

Mean visits every participating sample for each retained plan. Lexicographic
selection can stop at the first unique survivor, so equal runtime is not an
invariant. A shortlist bounds expensive after-placement probes, but does not
remove host/NUMA enumeration, auxiliary scoring, cold cache initialization or
refreshes after allocations and removals.

Use the same declared catalogue, copy cap, cache size, dataset/scenario digest,
GPU model and limit policy for comparisons. Include Random28 with both final
objectives and `uniformExtras=true` for RL-pool attribution. Compare cumulative
admissions, active peaks by resource and latency separately. Equal seeds pair
experiments but do not keep their later states or random draws identical after
different commits.
