# Как запустить сравнение алгоритмов и получить таблицы

Это руководство для запуска из терминала на macOS или Linux. Понадобятся
репозиторий и готовые датасеты; сами датасеты в репозиторий не входят.

Здесь используются два скрипта:

- [`run-benchmarks.py`](run-benchmarks.py) запускает выбранные алгоритмы на датасетах
  и сохраняет результаты каждого запуска отдельно.
- [`render-benchmarks.py`](render-benchmarks.py) превращает эти результаты
  в таблицы Markdown, CSV и PNG. В заголовке будут имя облака и режим B1/B100.

## 1. Подготовить окружение

Все команды ниже выполняются **из корня репозитория**. Перейдите в свой каталог:

```sh
cd /path/to/pod-placement-bench
```

Нужны:

- **Python 3.9 или новее** — для обоих скриптов.
- **JDK 25** — для Java-движка. Скрипт сам запускает Gradle, собирает приложение
  и выбирает Java 25 для бенчмарков. При первой сборке нужен доступ к сети
  для скачивания Gradle и зависимостей.
- **Z3 в `PATH`**, если выбран `smt`. Он входит в полный набор алгоритмов ниже.
  Проверить установку можно командой `z3 -version`.
- **Pillow и шрифт с кириллицей** — только для PNG. Для Markdown и CSV
  дополнительные Python-пакеты не нужны.

Подготовьте Python-окружение для всех трёх форматов:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install Pillow
```

Далее команды используют `.venv/bin/python`, поэтому активировать окружение
не требуется. Если нужны только Markdown и CSV, можно пропустить этот шаг
и заменить `.venv/bin/python` на `python3` во всех примерах.

Каждый бенчмарк запускается в отдельной JVM с пределом Java-кучи 6 GiB.
Оставьте также память для операционной системы. Бенчмарки выполняются последовательно.

## 2. Указать каталог с датасетами

Задайте путь к общему каталогу. **Замените путь в этой команде на свой:**

```sh
export PLACEMENT_DATASETS="/absolute/path/to/datasets-v2"
```

Ожидаемая структура:

```text
datasets-v2/
├── dc/
│   └── mixed-v2/
│       ├── snapshot.pb
│       └── operations.pb
├── ec/mixed-v2/…
├── sc/mixed-v2/…
├── zc/mixed-v2/…
└── uc/mixed-v2/…
```

В каждом выбранном облаке нужны оба файла. `--datasets-root` указывает
на общий каталог `datasets-v2`, а `--clouds` выбирает его подкаталоги.
Имена каталогов облаков должны быть в нижнем регистре.

Подкаталог `mixed-v2` используется по умолчанию. Если он называется иначе,
задайте `--dataset-subdir ИМЯ`. Допускается и более простая структура:
`datasets-v2/dc/snapshot.pb` и `datasets-v2/dc/operations.pb`.

Движок использует нормализованный поток создания и удаления pod/shard
и начинает размещение с пустого облака. Занятость из snapshot не восстанавливается.
Подробнее о поддерживаемых сценариях — в [описании датасетов](../one-cloud-schedulers-benchmark/docs/runner/README.md#joint-workload).

## 3. Проверить запуск на коротком фрагменте

Начните с одного облака и двух алгоритмов:

```sh
.venv/bin/python tools/run-benchmarks.py \
  --datasets-root "$PLACEMENT_DATASETS" \
  --clouds dc \
  --algorithms fitcount geometric-best-fit \
  --bulk-sizes 1 \
  --max-operations 100 \
  --output results/smoke
```

Скрипт соберёт приложение и выполнит два запуска. Прогресс будет виден
в терминале, например:

```text
[1/2] dc--B1--fitcount: running
  success (…s)
```

`--max-operations 100` ограничивает воспроизведение первыми 100 операциями
нормализованного сценария. Это не обязательно 100 pod или 100 запросов:
в потоке есть и удаления. Загрузка и подготовка полного входного датасета
всё равно выполняются, поэтому на большом облаке даже такая проверка может
занять заметное время.

Это проверка работоспособности, а не итоговое сравнение алгоритмов.
Построить её таблицу можно сразу:

```sh
.venv/bin/python tools/render-benchmarks.py results/smoke --format markdown
```

Откройте `results/smoke/tables/dc-B1.md`. В заголовке будет явно указан префикс
из 100 операций.

## 4. Запустить полный набор: DC → EC → SC → ZC → UC

В [`benchmark-algorithms.json`](benchmark-algorithms.json) собраны 32 конфигурации:
варианты FitCount, геометрические и ML-гибриды, пакетные алгоритмы, стратегии
Kubernetes, FGD, `yp-light` и `yp-planner`. Файл также хранит параметры вариантов,
включая FC1; его можно просмотреть перед запуском.

Для полного сравнения используйте **новый каталог результатов**:

```sh
.venv/bin/python tools/run-benchmarks.py \
  --datasets-root "$PLACEMENT_DATASETS" \
  --clouds dc ec sc zc uc \
  --dataset-subdir mixed-v2 \
  --algorithms-file tools/benchmark-algorithms.json \
  --bulk-sizes 1 100 \
  --output results/cloud-comparison
```

Это **320 отдельных запусков**: 5 облаков × 2 режима × 32 конфигурации.
Сначала пройдут все запуски DC, затем EC, SC, ZC и UC. Внутри облака сначала
выполняется B1, затем B100; внутри режима — алгоритмы в порядке JSON-файла.

- **B1**: по одному атомарному запросу за вызов планировщика.
- **B100**: в вызов передаётся окно до 100 атомарных запросов одного сервиса.
  Зависимости могут разбить запросы сервиса на несколько окон. Алгоритм
  без пакетной реализации обрабатывает запросы последовательно.
  Не каждое окно обязательно содержит 100 запросов.

Без `--max-operations` воспроизводится весь сценарий. Внешнего ограничения
по времени по умолчанию нет: полный набор на крупных облаках может работать
долго. Чтобы ограничить каждый запуск, добавьте, например,
`--timeout-seconds 3600` **до начала эксперимента**. В этот час входят также
загрузка данных и подготовка JVM.

### Какие настройки используются

«Полный запуск» означает весь поток операций. Каталог образцов, по которым
алгоритмы оценивают размещение, по умолчанию остаётся ограниченным:

| Параметр | Значение по умолчанию и смысл |
| --- | --- |
| `--catalogue-limit` | `32`: выборка до 32 начальных атомарных запросов для каталога. Число размещаемых запросов не ограничивает. Для полного каталога задайте `0`. |
| `--catalogue-weights` | `sampled`: частоты профилей берутся по выбранным образцам. |
| `--seed` | `44`: seed алгоритмов, у которых есть такой параметр; заменяет их seed из JSON-файла. |
| `--probe-cap` | `0`: диагностические физические пробы выключены, счётчики размещений и логические пики сохраняются. Собственные оценки FitCount работают. |
| `--gpu-model` | `devices20`: синтетические GPU с 20 долями. Это модель устройств, а не восстановленная физическая топология из production. |

Меняйте эти настройки до начала эксперимента и сохраняйте одинаковыми для
сравниваемых алгоритмов.

На macOS можно запретить автоматический сон на время команды: поставьте
`caffeinate -i` перед `.venv/bin/python`. На Linux запускайте команду как есть.

### Выбрать свои алгоритмы или параметры

Для простого списка замените `--algorithms-file …` на
`--algorithms fitcount geometric-best-fit bulk-fitcount`. Одновременно эти
два способа выбора не используются. Список доступных ID и параметры показывает
`./placement-bench algorithms` после сборки приложения.

Чтобы сравнить несколько настроек одного алгоритма, создайте свой JSON-файл,
например `local-algorithms.json`:

```json
{
  "fitcount": {"id": "fitcount"},
  "geo-20-4-4": {
    "id": "geometric-portfolio-mean-bulk-fitcount",
    "parameters": {"randomCandidates": 20, "geometricCandidates": 4, "leastCandidates": 4}
  },
  "geo-20-4-4-fc1": {
    "id": "geometric-portfolio-mean-bulk-fitcount",
    "parameters": {"randomCandidates": 20, "geometricCandidates": 4, "leastCandidates": 4, "randomPrefilter": true}
  }
}
```

Передайте `--algorithms-file local-algorithms.json` и новый `--output`.
Ключи слева — уникальные имена строк таблицы, `id` — зарегистрированный алгоритм,
`parameters` — его настройки. Варианты получают отдельные результаты.

## 5. Остановить и продолжить

Для остановки нажмите `Ctrl+C`. Уже завершённые результаты сохранятся.
Чтобы продолжить полный запуск из предыдущего раздела, повторите **всю исходную
команду**, добавив `--resume`:

```sh
.venv/bin/python tools/run-benchmarks.py \
  --datasets-root "$PLACEMENT_DATASETS" \
  --clouds dc ec sc zc uc \
  --dataset-subdir mixed-v2 \
  --algorithms-file tools/benchmark-algorithms.json \
  --bulk-sizes 1 100 \
  --output results/cloud-comparison \
  --resume
```

Если вы добавляли другие параметры, например `--timeout-seconds`, сохраните
и их. В новом терминале также заново задайте `PLACEMENT_DATASETS`.

Успешные запуски будут пропущены с пометкой `reused`. Прерванные, ошибочные
и превысившие время запустятся **с начала своего сценария**. Продолжения
с середины одного запуска нет.

Для продолжения должны совпадать датасеты и пути к ним, алгоритмы и их порядок,
параметры, исходники и ресурсы приложения, модели, настройки сборки,
скрипт запуска, Java и сохранённая сборка.
В частности, нельзя в том же каталоге поднять таймаут, поменять seed
или превратить короткую проверку в полный запуск. Для изменённого эксперимента
выберите новый `--output`.

## 6. Получить Markdown, CSV и PNG

Передайте **каталог всего эксперимента**, а не отдельный JSON результата:

```sh
.venv/bin/python tools/render-benchmarks.py \
  results/cloud-comparison \
  --format markdown csv png
```

Таблицы появятся в `results/cloud-comparison/tables/`:

```text
dc-B1.md       dc-B1.csv       dc-B1.png
dc-B100.md     dc-B100.csv     dc-B100.png
ec-B1.md       …
```

Можно выбрать один формат (`--format png`) или несколько. Без `--format`
создаётся Markdown. Другой каталог для таблиц задаётся через `--output`.

Скрипт можно запускать, пока бенчмарки ещё выполняются: он покажет готовые строки
и статусы остальных. После завершения запустите его ещё раз, чтобы обновить таблицы.

Шрифт с кириллицей выбирается автоматически из распространённых системных
шрифтов. Если подходящий не найден, добавьте, например,
`--font /path/to/DejaVuSans.ttf`, указав существующий файл.

### Относительно чего считается Δ avg

По умолчанию baseline — строка `fitcount` **в том же облаке и том же режиме B**:
B1 сравнивается с FitCount B1, B100 — с FitCount B100.
Положительная Δ означает большее время на запрос, отрицательная — меньшее.

Чтобы для обеих таблиц использовать FitCount B1, как в первоначальных слайдах,
добавьте `--baseline-bulk-size 1`. В таблице B100 заголовок столбца будет явно указывать на сравнение с B1.
При таком сравнении меняется также порядок обработки запросов между B1 и B100,
поэтому разница включает влияние этого порядка.

Для другого baseline используйте `--baseline ИМЯ_СТРОКИ`. Это именно ключ
из файла алгоритмов, а не обязательно его `id`. Если успешного baseline нет,
Δ будет недоступна.

### Как читать таблицу

Строки отсортированы по убыванию числа успешно размещённых атомарных запросов.
Baseline подсвечен в PNG. В CSV значения разделены по числовым столбцам,
чтобы их было удобно анализировать дальше.

| Столбец | Что он означает |
| --- | --- |
| `avg, мс` | Суммарное время обработки вызовов планировщика, включая проверку и фиксацию размещения, / число всех попыток, включая отказы. В B100 это время на запрос, а не на целое окно. Загрузка датасета и инициализация алгоритма в него не входят. |
| `Размещено: запр. / участ.` | Накопленное число принятых атомарных запросов и отдельных ресурсов POD/SHARD в них. Pod вместе с regular shard может быть одним запросом с несколькими участниками. Повторное создание после удаления учитывается снова. |
| `Пик активных: запр. / участ.` | Наибольшее число запросов и ресурсов, размещённых одновременно. |
| `Пик CPU`, `RAM`, `дисков`, `GPU` | Максимумы размещённых логических запросов на ресурсы, а не измеренное потребление. Максимум каждой величины ищется отдельно: они могут приходиться на разные моменты. CPU разделён на prod/nonprod, RAM и диски приведены к TiB; GPU — NVIDIA. |

Каждая строка получена одним воспроизведением в новой JVM, без отдельного
прогрева и повторов. Для устойчивых выводов о скорости нужны повторные
эксперименты в одинаковых условиях. Режим с прогревом и несколькими измерениями
описан в [руководстве CLI benchmark](../one-cloud-schedulers-benchmark/docs/runner/README.md#experiment-matrix).

Алгоритмы с переселениями, включая `yp-planner`, попадают в отдельные файлы
`dc-B1-relocations.*`, `dc-B100-relocations.*` и аналогичные для других облаков.
В них также есть FitCount и `yp-light` для сравнения, если они запускались.
У `yp-planner` столбец `avg работы` включает планирование и обслуживание
отложенных запросов (`maintenance`) на исходную попытку размещения.
Это затраты работы, а не время ожидания принятого запроса; компонент maintenance
показан отдельным столбцом.

## Где искать результаты и ошибки

В каталоге эксперимента сохраняются:

| Файл или каталог | Содержимое |
| --- | --- |
| `manifest.json` | Датасеты, алгоритмы, параметры и сведения о сборке. |
| `status.json` | Состояние каждого запуска и длительность по настенным часам. |
| `results/` | JSON завершившихся прогонов с метриками. |
| `logs/` | Диагностика отдельных прогонов, например `dc--B1--fitcount.log`. |
| `build.log` | Вывод сборки Gradle. |
| `runtime/` | Сохранённые JAR-файлы и сведения о Java. Нужны для продолжения. |
| `tables/` | Таблицы, созданные вторым скриптом. |

Статусы `TIMEOUT`, `ERROR`, `INTERRUPTED`, `PARTIAL`, `RUNNING` и `MISSING`
отображаются явно; незавершённые результаты не выдаются за ноль размещений.
После ошибки отдельного алгоритма скрипт переходит к следующему запуску
и возвращает ненулевой код завершения, если есть неуспешные строки.

Частые ситуации:

- **`Output is not empty`**: для нового эксперимента задайте новый каталог,
  для существующего используйте его исходную команду с `--resume`.
- **`Resume rejected`**: изменились входные данные, настройки или сборка.
  Начните изменённый эксперимент в новом каталоге.
- **Сборка упала до появления `manifest.json`**: прочитайте `build.log`, исправьте
  причину и выберите новый каталог. `--resume` требует готовый manifest.
- **Не найден Z3**: установите его и проверьте `z3 -version` в этом же терминале.
  Затем повторите запуск в новом каталоге, если manifest ещё не был создан.
- **Не строится PNG**: проверьте, что Pillow установлен в используемый Python,
  а выбранный шрифт существует и поддерживает кириллицу.

Полный справочник параметров доступен через `--help` у обоих скриптов.
Подробнее об устройстве эксперимента и метриках — в
[техническом руководстве](../one-cloud-schedulers-benchmark/docs/runner/README.md#batch-scripts-and-slide-tables).
