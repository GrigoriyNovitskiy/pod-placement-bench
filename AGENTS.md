# Правила разработки pod-placement-bench

## Перед изменениями

- Прочитай затронутый код и тесты, проследи обычный путь вызова и найди ближайший аналог в проекте. Сформулируй, какое поведение должно измениться и какие контракты нужно сохранить.
- До первой правки собери обсуждение из четырёх участников, включая ведущего. Два агента независимо предлагают варианты. Один ищет самый прямой путь, другой проверяет, можно ли решить задачу через существующие механизмы. Третий агент оспаривает оба варианта на конкретных сценариях. Ведущий проверяет, оправдана ли сложность каждого решения, и сводит обсуждение.
- Передай возражения авторам и дай им ответить или доработать варианты. Спорные доводы проверяй по коду, тестом или замером. Начинай реализацию, когда все четыре участника явно согласились с одной версией плана. Для небольшой правки достаточно короткого обсуждения. Если подагенты недоступны, проведи разбор самостоятельно и укажи в отчёте, что кворум не состоялся.

## Реализация

- Выбирай самое простое решение, которое полностью покрывает задачу. Используй существующие типы и механизмы, где они подходят по смыслу. Новый класс, слой, настройка или зависимость должны решать конкретную проблему этой задачи.
- Следуй стилю соседнего кода в именах, форматировании и использовании Java. Пиши комментарии только в действительно сложных и неочевидных местах, где без пояснения легко нарушить инвариант или неверно понять причину решения. Обычно достаточно ясных имён и структуры кода.
- Держи diff в границах задачи. Сохраняй пользовательские правки, совместимость Java API и существующих protobuf-датасетов, если задача явно не меняет контракт. Попутные переименования, форматирование и рефакторинг оставляй для отдельных изменений.
- Соблюдай правила бенчмарка из README модуля и `FITCOUNT.md`. Используй общую валидацию размещения и сохраняй атомарность запроса. Алгоритм должен выбирать размещение по доступному на этот момент состоянию. При изменении горячего пути проверь аллокации, повторные обходы и рост памяти с размером входа. Ускорение подтверждай сравнением до и после на одинаковом сценарии с тем же seed и режимом кэша.

## Тесты и самопроверка

- Добавляй тест, когда он ловит конкретную регрессию или фиксирует новый контракт. По умолчанию добавляй сценарий в существующий тестовый класс и используй `TestModel`, где он подходит. Отдельный класс оправдан для самостоятельного контракта. Для исправления бага по возможности проверь, что тест падает на старом коде по ожидаемой причине.
- После реализации перечитай весь diff, включая новые файлы. Проверь корректность на обычном пути вызова и на затронутых границах. Отдельным проходом ищи лишние изменения, абстракции без пользы и лишнюю работу на горячем пути. Каждый оставшийся фрагмент diff должен помогать решить задачу или проверить результат.
- Исправляй найденные проблемы и повторяй ревью и затронутые проверки, пока очередной проход не выявит конкретных замечаний. Перед завершением запусти `git diff --check` и `./gradlew :one-cloud-schedulers-benchmark:build`. В отчёте укажи фактические результаты и проверки, которые не удалось выполнить.
